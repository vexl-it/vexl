Part 1

TL;DR for business

What we measure and why. Funnels (first open to registration to first offer or request), weekly and monthly activity, whether offers get requests and requests get answers, club adoption, notification and pop-up outcomes, and how people come back after going quiet. The point is to answer product questions like "where does onboarding lose people" and "do club joiners ever use the main marketplace", not to follow individuals.

Two privacy rules, no exceptions. First, no exact timestamps leave the phone: only a day, an ISO week or a month, and every duration is turned into a coarse bucket (for example "1 hour to 1 day") on the device. Second, there is no user id and no device id on the server. Every row carries a random id that belongs to one flow or one calendar bucket and is wiped once that flow ends. In practice this means we can count, compare weeks and read funnels, but we can never open a table and look at one person, and two rows from the same phone cannot be linked to each other.

Journeys

One predefined flow on one phone, reported as a single state that gets replaced at each milestone. Example: the onboarding funnel. A phone that reaches "code verified" but never "registered" stays in that state; after 7 days the dashboard counts it among the drop-offs at that step.

Aggregations

Capped counters per calendar bucket, one row per phone per bucket. Example: the weekly marketplace counters. A phone adds up "marketplace opened" (cap 50) and "offers created, main" (cap 20) for the week and uploads that total; the dashboard sums rows into "how many instances did at least one".

Numbers are "reporting instances", never users. A reporting instance is one app install with analytics enabled that uploaded at least one row. A person with two phones is two instances; someone who reinstalls or logs out and back in is a new instance. Every chart says "reporting instances" and the backend user totals are shown separately and never used as a denominator.

What the dashboard will and will not show. Any group smaller than 20 reporting instances (a small country, a small club cohort, a rare notification type) is hidden or merged into "other". Cohorts appear only after they mature: a 31-day journey cohort is drawn when the last possible start plus grace has passed, a weekly bucket 14 days after the week ended. Every cohort has an "unknown" share: phones that stopped reporting because of a reinstall, logout, data loss or opt-out. "Unknown" is never labelled churn.

Opt-out. Analytics is on by default and can be switched off in Settings. Switching it off deletes everything queued on the phone and stops recording; the rows already on the server keep their last state and expire on schedule. There is no "opted out" row, and there is no sampling beyond the opt-out.

What is deliberately not built. No D90 retention (a 91-day id behaves like a device id), no "actions before churn" snapshots (a per-device record overwritten on every start is a standing profile), no per-day activity bits on client records, no A/B variants. Feedback ratings stay in the feedback service.

Three questions business still owes an answer to

  • Acquisition source (Q9). Vexl has no campaign, referral or link-source concept, so every "by source" metric is deferred. Is knowing the source worth adding an optional "how did you hear about Vexl" picker to onboarding (a closed list: event, friend, social, press, organic, unknown), or do we drop these metrics until a campaign programme exists?
  • Completed trades (Q10). Vexl cannot see a trade. The only way to count completions is one optional question at the existing post-chat feedback prompt (traded, met but no trade, no meeting, prefer not to answer), counted on the device and never stored next to free text. Do we add that question, or does the whole completed-trade group stay deferred?
  • Session tracking (Q11). Sessions per user, session duration and depth need a tracker that runs on every foreground and background change and checkpoints to storage every 30 seconds. Weekly and monthly activity already answer "who was active". Is the extra bookkeeping worth it, or do we leave the sessions category out?

How the system works

A compact version of system.md. The metric files say what to collect; this says how.

Concepts

Concept Meaning
Journey One instance of a predefined flow on one device. The client owns a random journeyId, keeps the whole state locally, and every upload replaces the state under that id. The server keeps the latest state only. The last state of a journey that never reached a terminal step is the churn signal.
Journey lifetime Declared per definition (7 or 31 days from startDay). After the terminal step or the lifetime the client deletes the id; the server nulls it after lifetime plus grace so the row can never be updated or linked again.
Aggregation Per absolute calendar bucket the client keeps capped counters and small enums and upserts them under a random per-bucket id. One row per reporting instance per bucket. Once the bucket is closed and the final flush acknowledged, the id is dropped.
Bucket Calendar-aligned, UTC: day, ISO week (Monday start) or month. Absolute, never relative to install or registration.
Settle period 14 days (tunable) after a bucket closes during which late flushes still land. Dashboards show a bucket as final only after it.
Reporting instance One app install with analytics enabled that uploaded at least one row for the population in question. All dashboard populations are counted in reporting instances, never users.
Core action Successful offer creation or successful messaging request. Re-requests and note-origin requests are excluded.
Creation class main when no clubs were selected, both when at least one was. No club-only class: the offer form always has a contact connection level.
Request class club when the offer reached the device only through a club, main otherwise. Taken from the offer's origin, never from which screen was open.

Long-lived journeys (over 7 days) carry booleans and enums only and never free numbers; country, platform and release line are row columns, not payload fields. Short journeys and aggregations may carry capped counters and duration buckets.

The server primitive

One endpoint on metrics-service, defined next to reportNotificationInteraction (the existing unauthenticated precedent): PUT /analytics/state, CommonHeaders only, callable before login, per-IP rate limit (24 h window, placeholder 300 calls), 4 KB raw body cap (413), payload cap in the schema (64 keys, strings up to 32 chars, integers up to 1000), success 204. Staleness is rejected with 400: a journey whose startDay is older than lifetime plus grace, or an aggregation past bucket end plus settle.

  • Start flush: an in-app loading task (runOn: 'start', no login required) drains the outbox including nextStart entries, after a random 0 to 60 s delay so it does not line up with the refresh calls made at the same moment.
  • Background flush: useAppState on background (not iOS inactive) sends now entries with a short timeout. Losing it is fine; the next start catches up. No background task and no push-driven flush.
  • Pre-login: the onboarding journey starts before a session exists, so the rest-api client function builds the request with makeCommonHeaders only and never calls getUserSessionCredentials.
  • Opt-out: preferencesAtom.analyticsEnabled, default true, toggle in Settings. Off clears the outbox, deletes all local ids and stops recording; on again starts fresh instances. The opt-out state itself is never reported.
  • Failure modes: logout, reinstall and silent MMKV loss end open journeys at their last server state (counted as unknown at maturity); a killed process loses nothing because the outbox is durable; days offline are bounded by one outbox entry per open id; a 4xx drops the entry and reports name and status only; clock skew is tolerated one day forward.

Dashboard rules

  • Every chart states its population as reporting instances on a release line that ships the definition. Backend counts (NUMBER_OF_USERS, COUNT_OF_ACTIVE_USERS) are shown separately and never used as a denominator for frontend rows.
  • Any group under 20 reporting instances (cohort week, platform, release line, state value, country) is hidden or merged into "other", applied after filtering.
  • Journey cohorts appear after lifetimeDays + graceDays since the last possible startDay; aggregation buckets after bucketEndDay + settleDays. Immature buckets are provisional or absent.
  • Outcome categories are terminal states, open and unknown. Never label unknown as churn.
  • apps/dashboard-app needs a new read-only connection to the metrics database; mixed metrics take their backend half from the existing metrics table.

Privacy analysis in short

Attacker model: full read access to analytics_states. Per row they learn platform, release line, phone country prefix (none for clubs), a definition name, a start day, an update day (week for long journeys) and a small enum or capped-counter state. They cannot learn who the instance is (no phone number, hash, IP, device model, installation id or session token), when exactly anything happened (day or week granularity; the upload time is not stored), or whether two rows belong to the same device (independent random ids, and rows share nothing but platform, release line, country prefix and start day).

Two residual risks are handled by policy, not schema. In a small population (a new release line on its first day, a small country) the shared tuple can be a group of one; suppression hides it on the dashboard, and the rule is to never add dimensions. Timing joins with backend rows that carry exact timestamps are broken by delayed initial and club uploads, day granularity and the absence of write timestamps; Postgres xmin, pk order and access logs remain as weak side channels, which is why the ingress requirement is mandatory. Clubs are tiny, so club definitions carry no country, round to week and are always delayed. Long-lived journeys are the most linkable objects because an id lives 30 days: they carry booleans and enums only, one journey per milestone, never chained. The endpoint is unauthenticated, so junk writes are possible; schema validation, caps, the body limit, rate limiting and dashboard suppression bound the damage to noise.

Decisions taken

  • Core action = successful offer creation or successful messaging request. Re-requests and note-origin requests are excluded.
  • Creation class: main when no clubs were selected, both when clubs were selected. No club-only class exists.
  • Request class: club when the offer reached the device only through a club, main otherwise. Classification comes from the offer, never from the screen, so no route param for the UI surface is added.
  • Country is stored on journeys and aggregations alike (except club definitions); the dashboard suppresses small groups.
  • Daily active users come from the backend refresh metric only. Client activity records are weekly and monthly flags with no per-day bits.
  • "Before churn" snapshots are rejected: a per-device record overwritten on every start is a standing device profile.
  • Initial journey uploads and all club uploads are delayed to the next app start so they cannot be timed against backend rows.
  • Long-lived journeys (30 days) carry booleans and enums only, one journey per milestone, never chained. D90 retention is not built.
  • Missing data is "unknown", never churn. MMKV is wiped on logout and data loss happens; a reinstall or re-login is a new instance.
  • Onboarding is a 7-day journey ending at onboardingFinished. Activation, activation latency and D1/D7/D30 live on registrationCohort, a 31-day journey from registration.
  • Reactivation is a 7-day write-once reactivationEpisode journey carrying the gap bucket, first action type and club membership. Time to the next dormancy is computed from local markers at the next episode.
  • Owner-side and requester-side outcomes use local 7-day window records per owned offer and per sent request, rolled into weekly counters. Nothing per offer or per request reaches the server.
  • Exposure journeys enrol only campaign-like notifications (product, inactivity, new offers, marketplace ready, new contacts, club admission, new content). Chat notifications are counted in weekly counters only.
  • Minimum suppression group is 20 reporting instances.
  • Backend DAU and WAU: extend the existing active-users job in contact-service with 1-day and 7-day rolling windows, labelled rolling.
  • Club join totals are read from the contact-service member_count_changes table, which already counts both join paths.
  • Notifications sent by type: add notificationType to NOTIFICATION_SENT; no Expo ticket handling.
  • Also from system.md: buckets are UTC; revision resolves retry ordering with no server timestamp; rejected payloads are dropped, not dead-lettered; opt-out defaults to enabled and wipes local state; first-release scope is decided later, not by the CSV priority column.

Q9: Acquisition source

Affects: Registrations by acquisition source, Activation by acquisition source, Number of new users from events, Activation of users from events, the source slice of Activation rate by event by channel or source, Churn by acquisition source, Reactivation by acquisition source.

No campaign, referral, link parameter or install-referrer concept exists, so every "by source" metric is deferred. Business needs to decide whether a source signal is worth an extra input, and which one.

  1. Do not build; the "by source" metrics are dropped and re-opened when a campaign programme exists.
  2. Add an optional "how did you hear about Vexl" picker in onboarding with a closed list (event, friend, social, press, organic, unknown), stored on the device and copied onto the onboarding and registration journeys. The only option that works on both platforms and keeps the value a small enum, if the metrics are wanted.
  3. Add a source parameter to app.vexl.it/link/ handled before login; covers links only and needs the initial-URL handling moved out of the logged-in hooks.

Q10: Completed trades

Affects: the three optional questions, Number of completed trades, Open chat to completed trade ratio and time, Post-trade return rate, Users who completed more than one trade, Average time between trades.

Vexl cannot observe a trade. The only way to get a completion signal is one optional structured question at the existing post-chat feedback prompt, kept out of the feedback-service row and counted as client aggregation. Should that question be added, and if so which one?

  1. Add one question with the answers traded, met but no trade, no meeting, prefer not to answer. This unlocks "Did you connect successfully", Number of completed trades, Open chat to completed trade ratio, Post-trade return rate and Users who completed more than one trade as self-reported metrics; "Did it go well" and "Did this work out for you" are dropped as duplicates of the star rating; the two time metrics stay unmeasurable.
  2. No new question; the whole completed-trade group stays deferred.

Q11: Foreground session tracking

Affects: the whole Sessions category, Average time spent in app per day week or month, Sessions before reactivation.

Session metrics need a tracker that runs on every foreground and background transition, checkpoints foreground seconds to storage every 30 seconds and keeps a short ring of session starts on the device. Is that continuous bookkeeping worth it, given that the activity records already answer "who was active this week"?

  1. Build the tracker and ship Sessions per user, Sessions per active user, Session frequency, Session duration and Session depth as weekly histograms, with the first-open cohort metrics as a later step.
  2. Do not build; sessions stay deferred and the activity and retention records are the engagement measure.
